# API — Catálogos y cuentas del gerente (módulo 10)

Pantallas: *Catálogos* (diapositiva 29: **Sucursales**, **Rutas y precios**, **Vehículos**) y *Cuentas* (diapositiva 30) del **GERENTE**. Todos los endpoints exigen sesión con rol `GERENTE` (`RequiereRol`): sin sesión `401`, otro rol `403`. Formato: éxito `{ "data": ... }`; error `{ "error": { "codigo", "mensaje", "campos"? } }` (los `422` y algunos `409` traen `campos`). Las peticiones que escriben exigen `X-Requested-With: JATSA` (ver `auth.md`). **Nada se borra**: sucursales, vehículos y cuentas se **desactivan**, y una tarifa se **cierra y se reemplaza**. Por eso no hay rutas `DELETE`.

Tablas del script SQL: `Sucursal`, `Telefono_Sucursal`, `Ruta`, `Vehiculo`, `Usuario`, `Persona` (sin cambios al script). Las reglas de integridad que comprueba el servicio (formatos, rangos) repiten las `CHECK` del script para dar mensajes claros; la base sigue siendo la última barrera.

## Catálogos

### Sucursales
- `GET /api/catalogos/sucursales` → `{ sucursales: [{ codigo, nombre, departamento, provincia, distrito, direccion, telefonos: ["953123456"], activa }] }` (activas e inactivas).
- `POST /api/catalogos/sucursales` → `201 { sucursal }`. Cuerpo: `codigoSucursal` (3 letras + 3 dígitos; se guarda en mayúsculas), `nombre` ≤ 80, `departamento` ≤ 40, `provincia` ≤ 40, `distrito` ≤ 60, `direccion` ≤ 150, `telefonos` (hasta 5, 9 dígitos cada uno, sin repetir; se aceptan espacios y guiones). Código repetido: `409 sucursal_existente` (campo `codigoSucursal`). Alta y teléfonos en **una transacción**.
- `PUT /api/catalogos/sucursales/{codigo}` → `{ sucursal }`. Cambia datos y **reemplaza** los teléfonos (transacción). **El código no cambia** (el del cuerpo se ignora). `404 sucursal_no_encontrada`.
- `POST /api/catalogos/sucursales/{codigo}/estado` con `{ "activa": bool }` → `{ sucursal }`. **Desactivar** exige (con la sucursal bloqueada): sin personal activo (`409 sucursal_con_personal`), sin viajes programados ni en ruta (`409 sucursal_con_viajes`) y sin envíos en curso (`409 sucursal_con_envios`). Reactivar siempre se puede.

### Rutas y precios
- `GET /api/catalogos/rutas` → `{ rutas: [{ id, origen{codigo,nombre}, destino{...}, tipoEnvio, precioBase, precioPorKm, distanciaKm, tiempoHoras, vigenteDesde, vigenteHasta, vigente, costoBulto }] }` con **todas** las filas (vigentes y cerradas) por origen, destino, tipo y vigencia descendente. `costoBulto` = `Tarifas::costoBultoCentimos` (la misma fórmula que usa el cotizador y la formalización): SOBRE 8.00/0.005/230 km → `9.15`, PAQUETE 10.00/0.020/230 → `14.60`, 10.00/0.020/1010 → `30.20`, CARGA 40.00/0.080/1200 → `136.00`, SOBRE 8.00/0.005/100 → `8.50` (los valores de la diapositiva 29).
- `POST /api/catalogos/rutas` («Nueva ruta») → `201 { ruta }`. Cuerpo: `origen`, `destino` (códigos de sucursales **activas**, distintos), `tipoEnvio` (`SOBRE`/`PAQUETE`/`CARGA`), `precioBase` > 0 (hasta 2 decimales), `precioPorKm` ≥ 0 (hasta 3), `distanciaKm` > 0 (hasta 1), `tiempoHoras` entero 1–32767. La tarifa nace **vigente desde hoy** (fecha del servidor). Si ya hay una vigente para ese origen, destino y tipo: `409 tarifa_vigente_existente` (se usa «Nuevo precio»). El conteo se hace con las filas bloqueadas (`UPDLOCK, HOLDLOCK`): dos altas simultáneas no dejan dos vigentes.
- `POST /api/catalogos/rutas/{id}/precio` («Nuevo precio») → `201 { ruta }` (la **fila nueva**). Cuerpo: `precioBase`, `precioPorKm`, `distanciaKm`, `tiempoHoras` (origen, destino y tipo no cambian). En **una transacción** con la fila bloqueada: cierra la vigencia de la actual (`vigenteHasta` = el día anterior a hoy) e inserta otra con `vigenteDesde` = hoy. **Los bultos ya cobrados conservan su tarifa**: `Bulto.costo` ya está guardado y `Bulto.idRuta` sigue apuntando a la fila cerrada, que no se modifica ni se borra. Errores: `404 ruta_no_encontrada`, `409 tarifa_cerrada` (la fila ya no es la vigente) y `409 tarifa_cambiada_hoy` (la fila entró en vigor hoy: cerrarla con «ayer» violaría `CK_RUTA_VIGENCIA`; el cambio se registra desde mañana).

### Vehículos
- `GET /api/catalogos/vehiculos` → `{ vehiculos: [{ placa, tipoVehiculo, capacidadKg, activo, viajesAbiertos }] }` (`viajesAbiertos` = viajes sin llegada).
- `POST /api/catalogos/vehiculos` → `201 { vehiculo }`. `placa` `ABC-123` (mayúsculas), `tipoVehiculo` (`CAMION`/`FURGON`/`CAMIONETA`/`MOTO`), `capacidadKg` > 0 (hasta 2 decimales). Repetida: `409 vehiculo_existente`.
- `PUT /api/catalogos/vehiculos/{placa}` → `{ vehiculo }`. Cambia tipo y capacidad; **la placa no cambia**. La capacidad no puede ser menor que el mayor peso ya cargado en sus viajes sin llegada (`409 capacidad_menor_a_la_carga`, campo `capacidadKg`).
- `POST /api/catalogos/vehiculos/{placa}/estado` con `{ "activo": bool }`. Desactivar con viajes programados o en ruta: `409 vehiculo_con_viajes`.

Los vehículos y sucursales inactivos **dejan de ofrecerse** donde ya se filtraba por `activo`/`activa` (programar un viaje en Despacho, Agencias y Salidas públicas).

## Cuentas

- `GET /api/usuarios?q=&rol=&estado=` → `{ cuentas: [{ usuario, persona, rol, sucursal: {codigo,nombre}|null, activa, esUsted, editable }], hayMas }`. `q` ≤ 50 (usuario o nombre), `rol` uno de los cinco, `estado` `ACTIVA`/`INACTIVA`; inválidos `422`. Hasta 200. **Nunca** devuelve el hash, documentos, teléfonos ni correos.
- `GET /api/usuarios/persona?tipoDocumento=&numeroDocumento=` → `{ persona: { existe, nombreCompleto?, tieneCuenta? } }` (solo el nombre) para el formulario. Se registra **antes** que `/{usuario}`.
- `POST /api/usuarios` («Crear cuenta») → `201 { cuenta }`. Cuerpo: `tipoDocumento` (`DNI`/`CE`/`PAS`), `numeroDocumento`, `rol` (**solo `ADMINISTRADOR` o `TRANSPORTISTA`**), `sucursal` (obligatoria y **activa**: `CK_USUARIO_SUCURSAL`), `usuario` (4–30: letras, números, `.`, `-`, `_`; único sin distinguir mayúsculas), `contrasena` (8–72 bytes, distinta del usuario; se guarda con `password_hash` bcrypt cost 12 y **no se devuelve**). La persona **debe existir y no tener cuenta**: `404 persona_no_encontrada` (campo `numeroDocumento`) o `409 cuenta_existente`; usuario repetido `409 usuario_en_uso`.
- `PUT /api/usuarios/{usuario}` («Editar») con `{ rol, sucursal }` → `{ cuenta }`. Solo personal (`ADMINISTRADOR`/`TRANSPORTISTA`): cualquier otra cuenta `409 cuenta_no_editable`. Un transportista con viajes sin llegada no cambia de puesto (`409 transportista_con_viajes`); guardar sin cambios no es error.
- `POST /api/usuarios/{usuario}/estado` con `{ "activo": bool }` («Desactivar seleccionada»). Desactivar **no** puede ser: la propia cuenta (`409 no_puede_desactivarse`), el **último gerente activo** (`409 ultimo_gerente`; se cuenta con los gerentes bloqueados) ni un transportista con viajes sin llegada (`409 transportista_con_viajes`). Reactivar siempre se puede, **salvo** a un ADMINISTRADOR o TRANSPORTISTA cuya sucursal esté **desactivada**: `409 sucursal_inactiva` (se pide reactivar la sucursal o mover la cuenta con «Editar» a una agencia activa; mover una cuenta desactivada se permite). Esa comprobación se hace en la misma transacción, con la sucursal de la cuenta bloqueada (orden sucursal → gerentes → cuenta; si la cuenta cambió de sucursal entre la lectura y el bloqueo se reintenta, y tras 3 intentos `409 cuenta_modificada`). Las reactivaciones de gerente, cliente y empresario no dependen de ninguna sucursal. `RequiereSesion` comprueba `Usuario.activo` en **cada** petición: la sesión de una cuenta desactivada deja de valer enseguida.

## Concurrencia: orden de bloqueos del sistema
Las reglas «solo recursos ACTIVOS» y «no desactivar lo que está en uso» se deciden **dentro de la transacción, con las filas bloqueadas** (`UPDLOCK, HOLDLOCK`), nunca con una lectura anterior. Orden constante de bloqueos en todo el sistema: **sucursales (por id ascendente) → vehículo → usuario → filas de `Ruta`**.
- **Quien desactiva** (sucursal, vehículo, cuenta) bloquea su fila y, ya bloqueada, cuenta lo que depende de ella (viajes sin llegada, personal activo, envíos en curso, gerentes activos).
- **Quien crea algo que depende de un recurso** también lo bloquea y revalida `activo` antes del INSERT: *programar un viaje* (Despacho: sucursales, vehículo y transportista), *crear una cuenta de personal* (sucursal), *cambiar el puesto* (sucursal de destino y cuenta) y *Nueva ruta* (las dos sucursales).
- Resultado: o la desactivación llega antes y el alta ve el recurso inactivo y se niega, o el alta confirma primero y la desactivación ve el viaje/cuenta nuevos y se niega. No queda un viaje programado con un recurso inactivo.
- `DespachoRepository::crearViaje` ya no recibe ids resueltos fuera de la transacción: recibe placa, usuario y código de destino y llama a `$decidir` con `origenActiva`, `destinoExiste/Activa`, `vehiculoExiste/Activo` y `transportistaExiste/Activo` leídos bloqueados.
- **«Editar» el puesto** calcula si hay cambio comparando rol y sucursal pedidos con los **de la fila bloqueada** (`rolActual`, `sucursalActual`); sin cambios reales guardar no es un error y no exige viajes en cero.
- Si dos transacciones se cruzan y SQL Server elige una víctima (error 1205), la petición falla con un error interno sin dejar nada a medias; reintentar es seguro.
- Pruebas simuladas con **ganchos que reproducen la intercalación** (`backend/tests/catalogos.php`) y revisión estática del orden de bloqueos; **no prueban concurrencia real** (eso requiere la validación real propuesta abajo).

## Decisiones para revisar
1. **«Nueva cuenta de personal» usa una persona que ya existe** (la diapositiva pide solo «Documento de la persona» y `Persona` exige teléfono; `Usuario` es 1:1 con `Persona`). Si no existe se responde `404` con un mensaje claro; **no se crea la persona desde aquí**. Una persona existe, por ejemplo, como destinatario de una reserva. Alternativa: añadir nombre y teléfono al formulario para crearla (cambia la pantalla del prototipo).
2. **«Contraseña temporal» — resuelta con autorización del propietario (PR #11).** Todos los roles (GERENTE, ADMINISTRADOR, TRANSPORTISTA, CLIENTE y EMPRESARIO) pueden **cambiar su propia contraseña**: `POST /api/cuenta/contrasena` exige solo sesión vigente (`RequiereSesion`) y conserva la verificación de la contraseña actual, la validación de la nueva (8–72 bytes, distinta de la actual y del usuario), bcrypt cost 12, la renovación de la huella de la sesión actual y la invalidación de las demás sesiones. **El personal** llega desde su nombre en la cabecera a una pantalla **solo de cambio de contraseña** (`/gerente/contrasena`, `/administrador/contrasena`, `/transportista/contrasena`); no ve datos personales ni funciones de cliente. `GET`/`PATCH /api/cuenta` (teléfonos y correo) siguen **solo para cliente y empresario**. Procedimiento: el gerente entrega la contraseña temporal **en persona** y la persona la cambia en su primer ingreso desde esa pantalla. **No se fuerza** el cambio al primer ingreso (no hay indicador en la base y no se añade ni se cambia el esquema sin autorización): sigue siendo un riesgo residual hasta que se decida. Si se sospecha de una contraseña temporal, el gerente **desactiva** la cuenta.
3. **Roles creables:** solo `ADMINISTRADOR` y `TRANSPORTISTA` (personal de agencia). No se crean gerentes ni se cambia el rol de clientes/empresarios; **«Editar»** cambia solo rol y sucursal del personal.
4. **«Nuevo precio» no se repite el mismo día** (ver arriba): la vigencia no admite una fila de cero días (`CK_RUTA_VIGENCIA`). Se mantiene.
5. **Sin borrados:** la única sentencia `DELETE` del módulo reemplaza los teléfonos de la sucursal que se está editando (`Telefono_Sucursal`), dentro de la misma transacción.
6. **Desactivar una sucursal** exige que no tenga personal activo, viajes sin llegada ni envíos en curso, para no dejar operaciones huérfanas.
7. **Fuera de este módulo:** *Resumen* y *Viajes y flota* (módulo 11) y *Reportes y plantillas* (módulo 12, bloqueado) siguen pendientes.

## Validador real pm10: PREPARADO para revisión estática (NO ejecutado)
Archivos en `backend/tests/integracion/`: `validar-pm10.ps1` (orquestador), `escritura_pm10.php` (preparar / ruta-antigua / limpiar acotados al manifiesto), `pm10-funciones.ps1` (reglas puras) y `probar-pm10-funciones.ps1` (prueba sin base de datos, 20 comprobaciones). Reutiliza `api.ps1`, `leer.php` (solo SELECT) e `instantanea.php`. **No se ha ejecutado ni se ejecutará sin una autorización nueva y separada del propietario.**

**Tres aceptaciones obligatorias** (sin ellas sale con `exit 2` sin hacer nada): `-AutorizadoPorElPropietario`, `-AceptoAvanceIrreversibleDeIdentity` y `-ConfirmoUsoExclusivoDeLaBase` (nadie más usa la base durante el ensayo).

**Dos garantías distintas, que no se mezclan**
1. **Datos originales:** tras la limpieza, las 12 tablas deben quedar con las **mismas filas, checksum y hash de cada fila**. Si no, fallo (`exit 1`).
2. **Contadores IDENTITY (`IDENT_CURRENT`):** borrar **no** los restaura y una carrera perdida, un interbloqueo o un `ROLLBACK` también consumen valores; por eso **no se promete** que coincidan ni que su avance iguale el número de altas del manifiesto. Se **informa** el avance exacto por tabla, se exige que **ninguno retroceda** y que solo avancen las tablas que el módulo escribe (`Sucursal`, `Telefono_Sucursal`, `Ruta`, `Vehiculo`, `Persona`, `Usuario`, `Viaje`). `DBCC CHECKIDENT` está prohibido. **Alternativa preferible si el propietario la autoriza después:** una **base de pruebas aislada** (copia), donde ese avance no importa.

**Seguridad de los registros temporales**
- Solo nombres temporales: sucursales `PMX901`–`PMX904`, vehículos `PM1-901`–`PM1-904`, personas `90000101`–`90000106`/`90000108` y RUC `20000000107`, cuentas `pm10_*`. Precondiciones de solo lectura: ninguno existe ya, y la fecha de la máquina coincide con la del servidor SQL.
- **Identificación de las filas temporales (corregida):** ya **no** se usa «id > `IDENT_CURRENT` inicial». Si una tabla con IDENTITY estaba **vacía**, `IDENT_CURRENT` devuelve la semilla (1) y la primera fila creada puede recibir ese mismo id, con lo que la limpieza habría fallado con una fila de prueba viva. El manifiesto guarda ahora el **conjunto real de ids** de cada tabla en la instantánea inicial (`idsAntes`, posiblemente vacío, que debe existir) y `pm10_reglas.php` clasifica cada tabla: una fila es **propia** solo si su clave está en el manifiesto y su id **no** estaba en esa lista; si una clave del manifiesto coincide con una fila que ya existía es **original** (aborta); y cualquier fila nueva que no sea del manifiesto es **ajena** (otro proceso escribió o quedó algo sin anotar) y también aborta, sin borrar nada. Se cubre además `Envio_Viaje` (la prueba no carga envíos: no puede haber cargas nuevas). **Esto tampoco prueba la autoría ante escrituras externas simultáneas**; por eso el ensayo exige uso exclusivo de la base (`-ConfirmoUsoExclusivoDeLaBase`) o, mejor, una base aislada.
- **Manifiesto** en disco, anotado **antes** de crear y tras cada cambio; `Test-ManifiestoPm10` rechaza cualquier valor que no sea temporal (un dato original jamás llega al PHP). La única tarifa que se cierra es una **temporal** (`ruta-antigua` la crea con `vigenteDesde` = anteayer, porque «Nuevo precio» se rechaza el mismo día).
- **Limpieza** (`limpiar`), todo o nada: verifica que cada fila a borrar tiene un id **mayor** que el `IDENT_CURRENT` inicial; que nada ajeno depende de lo temporal (viajes, cuentas, cargas, reservas, bultos, tarifas con una sucursal original, personas con reservas); y borra en **una transacción** `Viaje → Telefono_Sucursal → Ruta → Usuario → Persona → Vehiculo → Sucursal`, verificando que cada `DELETE` afecta exactamente lo contado. Si algo diverge: no borra nada (código 4) y pide revisión. Nunca borra de `Pago`, `Envio`, `Reserva`, `Bulto` ni `Envio_Viaje`.
- Sesiones: se borran solo los archivos `sess_<id>` de las sesiones que abrió la prueba. Contraseñas efímeras en memoria (a PHP solo por variables de entorno del proceso hijo).

**Qué comprueba** (cada punto con su API y su `SELECT`): sucursales (alta, 409, edición con teléfonos, desactivar/reactivar); vehículos; cuentas (alta de personal para una persona existente, 404/409, rol no permitido, bcrypt en la base, 403 para el administrador); **reactivación de personal con la sucursal desactivada** (409 y luego mover + reactivar); rutas («Nueva ruta», 409, **«Nuevo precio»**: mismo día 409, tarifa antigua → fila vieja cerrada ayer con su precio, una sola vigente); Despacho con recursos temporales y las desactivaciones en uso; **cambio de la propia contraseña de los cinco roles** con dos sesiones por cuenta (la otra deja de valer, la anterior no ingresa, el personal sigue sin `GET /api/cuenta`); y **carreras reales** con sesiones propias: C1 dos cambios de contraseña con la misma anterior (**solo uno confirma y solo sirve su contraseña**; la perdedora puede ser `409 contrasena_modificada`, `422`, **`401 sesion_invalida`** —`RequiereSesion` ya vio el hash nuevo y cerró su sesión, legítimo y nunca llega a la actualización condicional— o un interbloqueo comprobado; un 401 por otro motivo no se acepta, y el 401 solo es válido si se comprueba que exactamente una petición confirmó), C2–C4 desactivar vehículo / conductor / sucursal de destino a la vez que se programa un viaje (nunca queda un viaje abierto con un recurso desactivado), C5 crear cuenta a la vez que se desactiva su sucursal, C6 dos «Nueva ruta» idénticas (una sola vigente), C7 dos gerentes temporales que se desactivan mutuamente (consistencia; ver límite abajo).
- **500 genéricos vs interbloqueos reales:** un HTTP 500 solo se acepta en una carrera si el **registro de la aplicación** (`storage/logs/app-AAAA-MM-DD.log`) muestra, durante esa carrera, un interbloqueo real (SQL `1205` / «deadlock»); un 500 sin esa evidencia es un **fallo**. Se cuentan por separado y se aceptan solo si el estado final es consistente; **no se supone que sean imposibles** (el orden de bloqueos sucursal → vehículo → usuario → rutas no cubre todas las rutas del sistema; por ejemplo, marcar la salida de un viaje bloquea `Viaje → Vehiculo → Usuario`).
- **Límite conocido:** la regla del «último gerente» no puede probarse contra la base real sin desactivar a un gerente **original**; queda cubierta únicamente por las pruebas simuladas.
- Cobertura completa solo si todas las secciones se ejecutan; un fallo o interrupción se informa como tal. `exit 0` únicamente sin fallos, con datos originales idénticos y sin restos pm10.
- **Comprobaciones hechas hasta ahora (sin base de datos):** analizador de sintaxis de PowerShell (0 errores en los tres `.ps1`), `php -l` del PHP, `probar-pm10-funciones.ps1` (20/20) y las pruebas de revisión estática del backend (`catalogos.php`).
- **Fallos fundamentales:** si falla un paso del que dependen las fases siguientes (crear sucursales, vehículos o cuentas, la tarifa, los inicios de sesión, el viaje temporal, el registro del cliente o del empresario), la validación **se detiene** (`Critico`), conserva el informe y hace la limpieza controlada, en lugar de seguir con supuestos falsos.
